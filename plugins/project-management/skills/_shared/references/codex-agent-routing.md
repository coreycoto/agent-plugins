# Codex agent routing

Project Management owns its specialized agents and their authored catalog.
Use its Setup action or $project-management:manage-codex-agents to install
these agents; another plugin's installation does not supply them. Native
hook approval and agent installation remain separate user choices.

| Previous helper | Plugin-owned agent | Current skill |
| --- | --- | --- |
| `dependency_patcher` | `pm_dependency_maintainer` | `delivery-lifecycle` |
| `docs_taxonomist` | `pm_documentation_steward` | `project-governance` |
| `governance_auditor` | `pm_governance_auditor` | `project-governance`, or the assigned planning/relationship skill |
| `merge_gatekeeper` | `pm_merge_reviewer` | `delivery-lifecycle` |
| `release_publisher` | `pm_release_preparer` | `publish-change` |

Assign an objective, exact candidate or accepted plan, owned local files or
read-only scope, validation and delivery stage. The parent owns unresolved
policy, composed GitHub plans, merges and publication. Choosing a role does
not grant a credential or provider capability. The role's sandbox default
does not override the parent's live permissions.

If these roles are unavailable, perform the authorized workflow in the
parent. Inspect the current spawn selector before claiming role usability.
Do not silently install another plugin or use its agents as a substitute.

Keep project policy, permission profiles and trusted CI snapshots local.
CI/cloud tasks do not inherit a developer's shared installation. Until native
discovery is verified, commit revision-pinned projections of these same
Project Management roles. Preserve existing role IDs and filenames when
workflow contracts depend on them, and keep an already-pinned consumer
skill contract until its runtime migration is separately qualified.
